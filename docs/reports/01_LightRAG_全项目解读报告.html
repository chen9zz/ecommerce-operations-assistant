正文中的【源码】指本地可定位实现；【背景】指论文或官方资料；【建议】指为学习或二次开发给出的工程判断。末尾的源码索引使用固定提交链接，避免上游更新后行号漂移。第二份报告中的电商系统是基于这些能力的设计，不是这个仓库已经实现的业务产品。

建议分三遍阅读：第一遍读第 1 至 4 章建立整体认识；第二遍读入库、检索和存储章节并对照代码；第三遍结合 API、评测和风险章节准备二次开发。不要以“能背出目录”为目标，而要能解释一份资料如何变成证据、一条答案如何从证据产生。

1. 项目究竟解决什么问题

LightRAG 是一个检索增强生成框架。它先把外部资料处理成可检索的文本块、实体和关系，再在用户提问时取回相关信息交给语言模型组织答案。它既有可嵌入 Python 程序的 SDK，也有可以独立运行的 API 服务和网页管理界面。

大模型的参数知识并不自动包含你的业务文档，而且知识可能过时。把所有文档放进提示词又会受到成本、上下文长度和干扰信息的限制。RAG 将问题拆成两件事：检索系统负责找到证据，生成模型负责依据证据表达答案。检索错了，再强的模型也可能把错误资料解释得很流畅。

LightRAG 的特色是同时利用“原文语义相似”与“实体之间的关联”。例如：某活动适用于某商品集合，商品属于该集合，某类优惠与另一类优惠互斥。分别位于多篇文档的这些事实，可以通过实体和关系组织起来。但是图谱仍然来自文本抽取，存在遗漏和错误，不能把边当作未经验证的业务真理。

从应用层次看，LightRAG 主要位于知识与检索层。它不是通用任务执行 Agent，也不会因为配置了多个模型角色就自动成为多 Agent 系统。若要执行查询订单、诊断活动、修改设置等任务，需要外层业务流程、工具接口与授权机制。

2. 背景：为什么从向量 RAG 走向图谱辅助检索

2.1 2020 年 RAG 研究与今天的工程实践

【背景】Lewis 等人的 2020 年论文讨论了将参数化生成模型与非参数知识检索结合，用外部证据支持知识密集型任务。今天常见的“切块、向量化、检索、拼接提示词”是这一思路的工程化家族，不应认为所有现代 RAG 系统都完整复现了论文训练方法。RAG 原始论文

一个常见基线是：文档分块，Embedding 模型把块编码成向量；问题也被编码为向量；向量库返回相似文本；生成模型根据文本作答。这种方法便于实现，也适合单点事实查询。遇到多文档关联、术语别名、跨章节例外条件时，单次相似检索可能只找到其中一部分。

2.2 图谱为什么可能有帮助

假设三份资料分别说：“夏季活动覆盖户外集合”“商品 P 属于户外集合”“清仓商品不参加夏季活动”。问题是“P 为什么没享受优惠”。只检索与 P 最相似的商品说明，可能遗漏活动排除条款；只检索活动介绍，又可能遗漏 P 的属性。图谱能把关系组织为额外的召回线索，再回到原文核实依据。

图谱不是免费收益。建图需要抽取模型调用、实体合并、关系维护和存储；错误的实体合并会把不相干资料连接起来。最终应比较它在目标问题集上带来的收益是否抵得上索引成本与查询延迟。

2.3 LightRAG 与 Microsoft GraphRAG 的关系

【背景】Microsoft GraphRAG 的经典流程包括实体关系抽取、图社区层次构建和社区摘要；其 global search 使用社区摘要回答全局问题。LightRAG 论文于 2024-10-08 首次提交，强调图结构与向量表示结合、低层与高层检索和增量更新。GraphRAG 官方说明；LightRAG 论文

两者都属于图增强 RAG，但同名模式不能直接互换。尤其不能把 Microsoft GraphRAG 的“社区摘要 global search”套到本地 LightRAG 的 global 实现上。后文以实际查询函数说明差异。

2.4 论文方法与当前仓库是两个层次

本地 1.5.8 已经有多种解析器、分块策略、模型角色、数据库适配、管理界面和故障恢复契约。论文用于理解设计动机；当前源码用于理解真实接口和运行行为。早期博客中只围绕一个 lightrag.py 文件的讲解，已经不足以覆盖这个版本。

3. 用一张系统图建立整体认识

最重要的切分是索引阶段与查询阶段。索引阶段一般发生在资料上传或更新后，主要成本是解析、抽取和向量化；查询阶段面对用户，主要关注证据质量、响应时间和成本。它们可能共享模型和缓存，但不应混成一笔无法解释的“LLM 耗时”。

5. 数据模型：一份文档会变成哪些东西

可以把原文理解为证据本体，把图谱和向量理解为寻找证据的索引。一个完整入库通常涉及以下对象：

对象 作用 不能混淆的概念
原始／规范化文档 记录内容、来源和文档身份 文件名不是版本，也不等于业务有效期
文档状态 记录待处理、处理中、成功、失败及恢复信息 上传成功不等于索引完成
文本块 chunk 承载检索与回答所需原文 token 不等于中文字符数
实体 entity 概念、组织、产品、活动等命名对象 同名不一定是同一业务对象
关系 relation 两个实体间的关联描述与来源 抽取关系不是经过规则引擎验证的事实
三组向量 实体、关系、文本块的语义搜索入口 图节点不是只靠图遍历找到的
来源追踪 将实体和关系追溯到 chunk 和文档 引用编号不是自动完成的事实核验
LLM 缓存 复用抽取、关键词或回答计算 命中缓存不代表资料仍处于有效期

一条关系的描述可能由多个块的抽取结果合并而来。图上展示的文字因此可能是加工后的摘要。回答关键问题时，仍应保留回到原文的能力，特别是例外条件、金额阈值和生效时间。

四种存储类型不是强制安装四套数据库。它们表示四类职责；一个 PostgreSQL 部署可以承担多种职责，图后端也可以另选 Neo4j。反过来，同一产品名称的数据库也不意味着应用层多步操作就自动拥有完整事务。

6. 入库流程：从文件到知识索引

6.1 先初始化，再插入

核心使用顺序是：创建 LightRAG 实例，注入模型与 Embedding 函数，调用 initialize_storages()，再执行 ainsert() 或查询，结束时调用 finalize_storages()。构造对象并不等于数据库连接、共享状态和存储生命周期已经准备好。示例程序的初始化顺序值得先理解，再替换为自己的模型服务。

SDK 可直接接受文本；服务端上传文件还要经历文件保存、解析路由和后台处理。长任务不应被理解为一次同步 HTTP 请求内做完所有事情。业务前端需要展示文档处理状态，而不是上传后立即承诺内容可查。

6.2 文档身份、内容与状态分开管理

当前实现区分文档身份、来源键和内容哈希，不能照搬“所有对象的 ID 都等于文本 MD5”的旧版解释。常规入库路径中，chunk 身份会结合文档 ID 与块序号；不同入口和自定义 KG 路径还可能采用不同构造方式。这样做有利于追踪一份文档贡献了哪些块，但也要求更新时正确处理旧块与派生索引。

文档状态是调度与恢复的关键依据。处理者通过共享状态、锁与通知协作；入库和处理可以并行，并不是 busy=True 就拒绝所有上传。清空、删除或特定扫描阶段需要更强排他条件。FAILED 文档不应被描述为无限自动重试：该分支要求显式的手动重试请求，再给失败文档一次处理机会。

主要状态是 PENDING → PARSING → ANALYZING → PROCESSING → PROCESSED，异常进入 FAILED。派生存储刷新完成后才记录 PROCESSED，但部分多模态软失败、内容截断或显式跳过图谱抽取也可能允许流程完成。因此 PROCESSED 表示流程状态，不保证每张图片、每条关系都被正确理解。

6.3 解析器的工作是保留结构，而不是直接回答问题

原始 PDF、Word、表格和 Markdown 都要变成可处理内容。当前解析层支持 legacy、native、MinerU 和 Docling 路由；原生 DOCX 解析器及外部 HTTP 解析适配器分别存在。外部解析能力需要对应服务与配置，并不意味着仅安装 Python 包就具备所有 OCR、版面和多模态能力。

解析质量决定后续上限。一张“适用条件”表若被拆成无表头的单行，即使实体抽取模型很强也可能误读；一个“以下情况不适用”的标题若丢失，后面的条目可能被错误理解为正面规则。多模态分析可利用 VLM 补充图片内容，但图片识别结果仍应标明来源和不确定性。

建议先用结构清晰的 Markdown／HTML 资料做首轮业务验证，再引入扫描 PDF；这样能够区分检索问题与 OCR 问题，减少一开始同时排查多个环节的成本。

6.4 分块策略决定证据边界

本地支持 F、R、V、P、C 等处理选项，对应固定 token、递归字符、语义向量、段落语义和自定义分块路径。不同分支有自己的前提，不能把所有选项当成简单替换一个数值。

策略 直观理解 优点 需要关注
固定 token 按长度切割并保留重叠 简单、可控、适合基线 条件与例外可能分离
递归字符 尽量沿较自然的分隔符切分 较好保留段落结构 文档格式不规范时仍可能断句
语义向量 用语义变化辅助判断边界 适合主题变化明显的文本 额外 Embedding 成本与阈值敏感性
段落语义 在段落结构上组织语义块 适合保留标题和正文关系 依赖解析结果与段落结构
自定义 业务方提供或调整块 可保留完整规则、表格 需要自行验证长度、身份和来源一致性

基础固定分块默认是 1,200 tokens、100 tokens overlap；实际运行可被配置覆盖。短块可能召回精准但缺少上下文，长块保留关系却增加噪声和生成成本。电商规则中“适用范围、例外、起止时间”最好共同保留，必要时将父标题和来源信息附到块中。

6.5 实体与关系抽取

抽取阶段让 EXTRACT 模型从每个块中提出实体名称、类型、描述，以及实体对之间的关系、关键词和描述。提示模板规定输出形式，代码负责解析、校验与容错。实体类型提示可做领域适配，但没有一个提示词能保证所有名称都映射成唯一的业务 ID。

例如：“冬季专场包含保暖系列，但预售商品除外。”可抽出“冬季专场”“保暖系列”“预售商品”等对象及其关系。问题在于“包含”“排除”的方向与条件必须被保留。若压缩描述只剩“活动与预售商品相关”，图谱虽然看起来连接丰富，业务意义已经丢失。

默认抽取文本采用 delimiter 格式：实体记录含类别、名称、类型、描述，关系记录含类别、两个端点、关键词与描述。当前常规关系会按排序后的端点对聚合，默认 NetworkX 使用无向图，关系默认权重也不是置信概率。因此“包含谁、排除谁”需要从描述、关键词或业务规则结构中保留，不能只靠一根带方向的图示箭头推断。

源码包含补充抽取机制。当前 entity_extract_max_gleaning 大于零时，该实现增加一轮补充抽取；不能直接宣称把参数设为 N 就执行 N 次补充循环。学习时应看循环与条件分支，而不是只依据参数名称猜测行为。

6.6 合并、摘要与来源关联

同一实体可能被多个块提及。合并需要汇总描述、处理类型、保留来源，并在描述过长时调用模型摘要。关系同样需要合并。图索引与实体／关系向量索引需要一起更新，否则可能出现“向量找到对象，但图里没有最新属性”的中间状态。

合并不能等同于完善的实体消歧系统。“会员”“VIP”“金卡会员”是否同一对象，要由领域定义决定；两个店铺都叫“夏季促销”的活动也不应被合并。业务系统可用规范 ID、别名表和版本前缀减少误合并，而不是把这一责任全部留给抽取模型。

来源追踪包括实体／关系对应的 chunk 集合，以及文档贡献的实体与关系锚点。它们不仅用于展示引用，还关系到删除时如何知道哪些派生对象应被修改。原文与索引的关联是核心数据契约，不是可有可无的 UI 装饰。

还要区分完整来源追踪表与图上用于检索的来源视图。默认 source_id 上限为 200，KEEP 策略保留较早来源；后续新描述可能因来源上限被过滤。完整追踪表增加了来源，不保证图描述已吸收每条新事实。这是应通过业务增量测试检查的细节。

写前恢复索引的顺序也很重要：先持久化文档候选实体／关系全集，再推进图写入状态，最后修改图。若进程中断，恢复程序仍能知道哪些对象可能受影响。候选全集不等于所有对象已经创建成功，合法的空索引也与索引丢失不同。

6.7 增量更新与删除为什么复杂

新增文档可以抽取后并入现有图，而不必总是从零建图。删除文档则更复杂：某实体可能同时被三份文档支持，删除其中一份不应删除整个实体。系统需要移除该文档贡献，保留其他来源，必要时利用抽取缓存重建描述和关系。

本地实现使用文档级贡献锚点与恢复记录；删除前无法证明来源归属的情形可以被拒绝，而不是贸然继续。另一方面，重建存在 best_effort 默认策略和缓存缺失等降级路径，不能声称删除后所有图谱语义必然等同于“只用剩余文档完全重建”的结果。

业务上应给更新建立明确验收：旧文档不可检索、共享实体仍存在、已删除来源不出现在引用中、失败记录可查，并按需要触发重建。知识库版本切换与回答缓存失效也要纳入更新流程。

“增量”至少有三种不同含义：新增文档加入现有索引；失败文档清理旧贡献后重处理；自定义 chunk patch 追加。普通重复 enqueue 不自动覆盖同名文档，修改 parser hint 也不代表系统一定重解析已经处理完的资料。业务更新流程应明确选择哪条入口。

7. 查询流程：一次回答究竟经过什么

7.1 六种模式的准确含义

模式 主要入口与证据 适合做什么实验
local 低层关键词检索实体向量，再取图中的实体及相关关系 明确实体的问题
global 高层关键词检索关系向量，再取关系和端点实体 围绕关系、主题的问题
hybrid 合并 local 与 global 的图检索结果 同时需要实体与关系线索
mix 图检索结果加原文 chunk 向量召回 兼顾关系线索与未被抽取的原文
naive 直接检索 chunk 向量，不使用图路径 基线或适合文本直接匹配的问题
bypass 跳过知识检索，走模型生成路径 排查生成层或对照实验

特别纠错：仓库 AGENTS.md 对 global 的概述包含 community/summary 字样，但本地 operate.py 的实际调用是关系向量检索及图属性获取。理解执行行为应以源码为准。global 也不意味着每次读取全图，更不等于自动进行任意长度的多跳逻辑推理。

7.2 关键词提取：实体线索与主题线索分开

KEYWORD 模型为问题生成高层和低层关键词。低层偏向具体对象，高层偏向关系或主题。调用方也可以通过参数提供关键词。关键词失误会影响图检索；mix 中原文块向量召回因此具有补充价值，但不能保证弥补所有抽取或关键词错误。

“这个活动呢”“它为什么不生效”这样的追问依赖对话中的对象。当前 QueryParam 的历史消息主要进入生成上下文，不应据此宣称检索阶段已经完整实现指代消解。面向业务时，可在外层把问题改写成带明确活动 ID 和时间的独立问题，再进入检索，并保留改写记录以便排查。

7.3 图路径：先语义找入口，再按关系补上下文

local 先对低层关键词查询实体向量，读取对应节点属性与图连接；global 先对高层关键词查询关系向量，读取边属性及端点实体。这样向量检索承担模糊匹配，图结构承担关联组织。它不是先把整个图送给模型，也不是每个问题都让模型生成 Cypher。

图路径随后需要找到支持实体或关系的原文块。只有摘要没有原文，很难解释具体条件；只有原文没有关联，又可能漏掉跨文档约束。LightRAG 组织两者是为了给最终生成提供更完整、可追踪的材料。

7.4 mix 如何合并结果

当前实现对实体／关系结果做轮询式交错与去重；来自不同检索来源的 chunk 也进行轮询合并与去重。轮询可以让一条来源通道不轻易淹没其他通道，但它并不是 RRF。RRF 需要按各列表中的名次计算并累积倒数分数，例如 sum(1/(k + rank))；本地这条融合路径没有这种求分行为。

如果二次开发想改成 RRF，应说明那是自己新增的融合实验，并同时比较收益、额外复杂度与跨通道分数解释。不要把自己知道的检索术语默认套到项目上。

7.5 重排序与 token 预算

初步召回追求不遗漏候选；reranker 用问题与候选文本的匹配程度重新排序，帮助在有限上下文中保留更有用的内容。它无法修复根本没有被召回的证据，也不等于判定规则是否适用于某个商家。

enable_rerank 默认开启，但若未配置可用的重排序函数，就不能声称实际执行了 rerank。应从日志和调用记录确认是否启用。重排序后的块还受数量与 token 预算约束；“向量库找到了某块”和“该块最终进入生成提示词”是两个不同的事实。

本地基础默认 值 含义
mode mix 默认查询模式
top_k 40 local 的实体或 global 的关系初始召回规模
chunk_top_k 20 文本块召回与保留相关限制
max_entity_tokens 6,000 实体上下文预算
max_relation_tokens 8,000 关系上下文预算
max_total_tokens 30,000 查询上下文总预算参数

这些是源码常量和参数默认值，不是某业务的最佳配置；环境变量和请求参数可能覆盖它们。旧示例中出现 top_k=60 不能被当作本地实际默认。总预算也不能替代对所用模型的输入、输出和历史消息空间的完整计算。

7.6 生成与引用

最终生成通常接收问题、格式化实体与关系、原文块、系统约束和可用历史。SDK 可以选择只返回上下文、只看提示词或生成答案；API 也有面向结构化检索数据的路径。这使开发者能把“检索对不对”和“模型回答对不对”分开检查。

引用支持将答案追溯到资料，但自动编号只是证据组织，不是每句话与来源的逻辑蕴含证明。比如来源写“部分套餐支持”，答案却写“所有商家都支持”，即使附着同一链接也仍是错误。需要额外检查结论、适用条件、时间范围是否一致。

8. 模型角色、Embedding 与缓存

EXTRACT 负责入库抽取和合并摘要；KEYWORD 负责查询关键词；QUERY 负责最终回答；VLM 负责图片相关分析。未指定独立角色配置时，角色可继承基础模型配置。它们是流水线职责划分，不是四个相互协商的 Agent。

Embedding 与上述生成模型不同：它输出数值向量，用于相似性检索。维度必须和索引一致，文档编码与查询编码也应采用兼容的向量空间。即使两个模型输出维度相同，也不能直接混用旧向量与新查询向量；应记录模型身份并按迁移策略重建索引。非对称 Embedding 中，query 和 passage 的指令或前缀可能不同。

配置多模型可以在速度、成本与质量间取舍。例如先用稳定的小模型试验关键词提取，把更强模型留给复杂答案；但是否节约成本必须统计真实调用。抽取质量差导致后续重建，可能抵消便宜模型的单次优势。

缓存需要区分阶段。抽取缓存帮助重试和图重建；关键词缓存可减少重复问题的解析；回答缓存可复用生成结果。当前查询链路中的回答缓存检查位于检索和重排序之后，因此命中并不意味着跳过全部检索成本。

本地回答缓存的身份不等同于完整业务有效性：它没有自动表达商家、活动配置快照、全部模型提供商参数与知识库内容版本。若政策或活动发生变化，业务系统必须制定命名空间或失效策略，不能仅用“缓存里有答案”判断可返回。

缓存存储本身受 workspace 隔离，问题是它不自动表达同一 workspace 内的全部业务变化，并非完全没有隔离。存在 conversation_history 时，当前实现绕过共享答案缓存的读写；真正的流式迭代器结果不会写入该答案缓存。多轮与流式体验的缓存收益应按实际路径测量。

9. 存储、并发与一致性

9.1 默认组合与替换能力

默认轻量组合围绕 JSON KV、JSON 文档状态、NetworkX 图和 NanoVectorDB 向量展开，适合小规模学习与验证。可替换后端包括 PostgreSQL、Neo4j、MongoDB、Redis、Milvus、Qdrant、Faiss、Memgraph、OpenSearch 等，但每种数据库只实现适合它的接口；不能把一串数据库名称理解为同时必须部署的依赖。

选择后端时先考虑数据规模、写入方式、备份与团队维护能力，再考虑技术名词的丰富度。仓库契约把五种文件后端限定为小规模测试验证，生产部署应选择服务端存储后端，并验证并发、连接池、超时、索引和备份恢复。源码中的可选适配器不等于本次已对所有数据库做过集成测试。

9.2 workspace 做隔离，但不自动完成授权

不同后端实现 workspace 的方式不同：文件子目录、集合名前缀、关系表字段过滤、向量 payload 分区等。workspace 是数据组织与隔离机制；“当前登录用户是否有权访问这个 workspace”仍是业务授权问题。

多商家应用需要由服务端根据身份决定租户范围，不能接受客户端随意提交的 workspace 后直接访问数据。检索、图扩展、原文读取、引用返回、缓存命中与导出都应遵守同一范围。检索完再把不该看的答案删掉，已经太晚，因为不该读取的资料可能已进入模型上下文。

9.3 多存储写入没有天然的全局事务

图、KV、向量与文档状态分别写入，中途崩溃会留下中间状态。即便统一到一种数据库产品，也要核实应用是否把这些写操作放在同一事务；当前项目的工程契约明确承认跨存储无整体事务。

代码通过状态记录、顺序约束、锁、来源锚点和重建来处理故障。理解“可靠”应具体到故障窗口：哪个写入已经持久化？哪些记录仍可重试？错误是否向上传播？下一次运行如何恢复？不要笼统称为强一致或 exactly-once。

9.4 文件后端不能一概而论

NetworkX、NanoVectorDB 和 Faiss 维护进程内副本，需要文件指纹与更新信号配合判断是否重载。图存储与向量存储在冲突处理上并不相同：图合并依赖先前读取的累计状态，不能简单模仿向量后端的重载和重放缓冲。

JSON KV 与文档状态在多 worker 场景使用共享字典语义，更新标记的含义又不同。这里最有价值的学习点是“不同数据结构需要不同一致性策略”，而不是记住一个通用加锁口诀。docs/design/ 中的文件快照、单写者、入库并发和删除恢复契约值得与对应实现一起读。

10. API 与 WebUI：框架怎样成为可操作的系统

10.1 服务层做了什么

FastAPI 层负责启动时模型配置与生命周期、认证、请求校验、查询、文档操作、图操作、健康检查及静态页面。核心角色配置有更新能力，但不能据此假定存在通用 REST 模型管理接口。查询路由捕获配置好的 LightRAG 实例，再把请求参数转换成核心查询参数。服务端默认端口配置为 9621，但实际部署可覆盖。

接口组 用途 业务接入重点
/query 一次性返回答案 返回体、超时和错误处理
/query/stream 逐步返回答案与引用 正确解析流式协议和中断
/query/data 返回检索上下文等结构化数据 评测、证据审查、外层编排
/documents/* 上传、扫描、状态、删除或重试 上传完成与索引完成分开
图相关路由 查看及编辑实体关系 只对授权人员开放管理操作
/api/* 兼容层 对接 Ollama 风格客户端 兼容接口不代表部署了本地模型

特别注意，/query/stream 使用 application/x-ndjson：每行一个 JSON 对象，开启引用时首行可包含 references，后面是响应片段。它不能被直接描述为 SSE。SSE 通常使用 text/event-stream 和 data: 等帧格式；两者都能流式传输，但客户端解析协议不同。

10.2 身份认证与业务权限

项目支持 API Key 和账号认证等机制。源码中的统一认证依赖保护查询与管理接口，但并没有因此自动提供按商家、角色、文档级别控制的完整 RBAC。隐藏某个按钮并不阻止用户直接请求接口。

默认监听地址、认证开关和兼容路由白名单都需要部署者明确检查。官方 README 提醒未配置认证时不要直接暴露服务；Ollama 兼容路径还有白名单配置。这属于实际配置边界，不需要把整个项目泛化成“不安全”，也不能因为有登录页就宣称完成企业权限系统。

具体默认包括 HOST=0.0.0.0，认证白名单含 /health,/api/*。因此即使为部分服务配置认证，兼容接口仍可能被白名单放行；应根据部署用途显式设置，而不是仅检查是否出现登录页。

10.3 前端是什么技术栈，展示什么

本地 WebUI 使用 React 19、TypeScript、Vite、Tailwind、Zustand 和 i18next；图可视化使用 Sigma／Graphology 相关库。界面围绕文档处理、知识图谱探索、检索问答与设置展开。图的可视化主要帮助观察与调试，节点多、连线密不等于检索效果好。

WebUI 的 /workspace 是页面入口概念，不应与“一个登录用户可以切换并隔离多个商家知识库”的业务能力混为一谈。核心路由使用的是服务端绑定的 LightRAG 实例。若二次开发成运营产品，建议另做面向任务的页面：活动选择、诊断结果、证据和缺失字段；保留上游界面作为管理与调试入口。

11. 配置、部署与运维如何理解

pyproject.toml 声明 Python >= 3.10，包名为 lightrag-hku；API、数据库、模型、评测和可观测性依赖通过 extras 分组。锁文件用于约束依赖版本。示例命令不意味着任意最新依赖组合都经过验证，复现时应记录 Python、锁文件、模型、后端和配置版本。

.env、env.example 和交互式环境向导负责模型、存储、解析、认证等配置。Compose 和 Kubernetes 材料用于部署组合。某些 Compose 文件由向导生成，应修改输入配置而不是把生成物当作唯一真相。开发环境和容器内服务地址也不同，不能把只在容器网络里可解析的主机名直接拿给宿主使用。

扩容有一个重要前提：同一 workspace 仅一个入库实例，共享状态不自动跨 pod。增加查询实例需要外部数据库、按要求初始化并保持单一写入入口；版本升级也需协调入库暂停。不能仅增加 Kubernetes replicas 就宣称支持并行入库和分布式一致性。

建议按以下顺序建立可复现环境：

  1. 固定当前提交，保存配置模板与依赖锁；不把密钥放进 Git。
  2. 先以少量纯文本、一个可用生成模型和兼容 Embedding 跑通 SDK 主路径。
  3. 验证文档状态、索引数量、检索原文和答案，而不只看首页能否打开。
  4. 再启动 API 与 WebUI，检查流式协议、认证和失败提示。
  5. 接入业务文档、reranker 与正式数据库后，重新建立质量和延迟基线。

Langfuse 等可观测性集成可以帮助追踪调用。业务系统至少应记录 request_id、检索模式、知识库版本、召回条目、最终上下文、模型标识、token、耗时和错误。记录时要控制敏感内容，尤其不能为了排查方便把密钥或不必要的订单个人信息写进日志。

成本应分阶段统计。一次查询成本近似为关键词模型、问题 Embedding、重排序和回答模型成本之和；索引成本还包括解析、分块向量化、实体关系抽取及合并摘要。缓存、批处理和并发会影响延迟与费用，但并发提高不保证吞吐无限增加，外部模型可能有速率限制。

12. 测试与评测：如何避免“看起来回答不错”

12.1 三类验证不能混为一谈

工程测试检查接口、状态和边界行为，例如解析失败、文档删除、缓存、并发锁、后端适配、前端组件。离线测试通常使用 mock，真实数据库和模型集成测试需要相应服务。测试存在不等于当前环境全部通过。

RAG 质量评估检查证据召回和答案质量；论文复现则要遵循其数据、问题和比较方法。仓库提供了 RAGAS 相关脚本、样例问题和论文复现材料。文档里的参考阈值不应直接变成你的业务验收标准；RAGAS 也并非每一个指标都不需要参考答案。

业务 拒答／追问正确率、诊断原因正确率 信息不足时是否保持合理行为
工程 p50/p95 延迟、索引耗时、单次费用 质量收益是否有可接受代价

对比实验至少固定文档版本、切分、Embedding、生成模型、提示模板、输出预算与问题集。先比较 naive、hybrid、mix，再单独开关 rerank；若同时换模型、加数据、改提示词，就难以知道收益来自哪里。还应报告图检索不占优的场景，例如单点事实查询、精确 SKU 检索或资料量很小的任务。

论文复现目录使用大范围问题和模型比较答案的评价方式；这类偏好或胜率不等于电商规则正确率。面向真实业务，最好人工核对关键判断与证据，用自动评分辅助扩大覆盖，并抽查评分者偏差。

13. 常见失败如何定位

现象 先检查什么 下一步
上传完成却查不到 文档状态是否 processed、是否选错 workspace 查看失败原因和索引状态
找到的资料不相关 问题是否明确、关键词与向量模型是否匹配 查看最终检索材料；原始候选需额外埋点
漏掉例外条款 分块是否切断标题和条件 调整分块并重建受影响文档
引用正确但结论错误 生成是否忽略否定、时间或适用范围 增加结构化判定与结论核查
图谱混入其他产品 实体同名、别名和版本策略 建立规范 ID 与隔离范围
更新后仍答旧内容 索引是否完成、缓存是否失效 绑定知识快照并做回归检查
查询延迟高 分阶段耗时、召回量、rerank 与模型调用 减少无效候选并选取合理模式
删除后部分描述仍旧 来源锚点、抽取缓存、重建策略与报告 检查降级记录，必要时重建

排查顺序应沿数据流推进：原文正确吗？解析正确吗？分块完整吗？抽取合理吗？召回正确吗？最终上下文包含证据吗？生成遵守证据吗？从“模型不够强”开始猜测，往往会错过真正问题。

14. 与 RepoPilot-R 的关系及学习路线

RepoPilot-R 重点是工具执行、任务状态、恢复和验收；LightRAG 重点是知识组织、检索、证据和生成。组合在简历中能形成两条独立故事。可以复用你在日志、接口、错误处理方面的经验，但没有必要把两个项目强行拼成一个复杂平台。

推荐按任务阅读源码：先从 SDK 示例和 QueryParam 跑通概念；再看 public query 分发与 operate.py 查询；随后回读 pipeline 和抽取；最后研究后端生命周期、删除恢复与 API。每读一段，都写出输入、输出、依赖、失败行为和可验证的假设。

建议做四个学习实验，均属于后续工作：只用 naive 建基线；对同一问题切换图检索模式；删除一份共享来源文档观察图与引用；对一个版本冲突问题查看缓存和知识库切换行为。实验日志比只保存成功截图更适合面试复盘。

15. 能力边界与结论

这份代码提供了功能较完整的知识索引和检索服务基础，尤其值得学习的是双层检索、来源追踪、可替换存储及复杂更新的工程处理。它不会自动解决每个业务的实体消歧、版本适用性、金额计算、权限隔离、答案核验或生产容量问题。

真正读懂项目的标志是能够回答：为何需要这条检索路径，哪些数据是原文、哪些是模型加工结果，出错后在哪里发现，以及性能结论如何被复现。后续电商应用应围绕这些边界增加明确的业务逻辑，而不是只改页面标题和提示词。

17. 检索进阶：面试追问时值得理解的细节

local 中实体保持向量命中顺序，图节点 degree 并不自动使实体重新排序；邻接关系按 (rank, weight) 元组降序，即先比 rank、相同再比 weight，不是两者算术相加。global 则保持关系向量命中顺序，再按关系端点出现顺序组织实体。这说明排序策略应分层解释。

图来源块的默认 VECTOR 选择方式，会在图限定的候选块内比较原问题向量；它不同于 mix 的全库 chunk 直接召回。相关块数量参数默认 5 也不等于每个实体固定拿 5 块：VECTOR 配额与去重后组数有关，WEIGHT 则按组的顺序递减分配。若做检索优化，应记录分支、候选、配额与降级原因。

最终上下文预算先限制实体和关系，再给原文分配剩余空间。截断倾向保留前部完整记录，不是遇到长记录就自动跳过去选短记录。历史消息、输出额度和协议开销还需要调用方管理。预览接口返回处理后的最终材料；想比较所有初始候选，必须增加观测点。

reference_id 是本次查询临时编号，同一 file_path 的块共享编号；它不能当稳定文档主键。业务系统应使用自己的版本化来源 ID，并把原文 URL、chunk_id 和规则条款关联起来。

关键词两组都提取失败时，源码有短问题回退和长问题直接返回失败的分支。因此 mix 不保证在任何关键词失败下都能靠 chunk 向量补救。此类失败应进入业务评测，而不能只用正常问题验证。

本次还发现值得后续复现的静态风险：非流式长回答有基于长度触发的提示词／字符串清理分支，naive 路径还会切去一段前缀。静态阅读无法证明实际输入一定触发问题；建议在短自定义系统提示词和长答案下补回归测试。此观察没有被当作已复现故障，也未在本次修改源码。入口为 operate.py 的 4954 与 7109 行。
